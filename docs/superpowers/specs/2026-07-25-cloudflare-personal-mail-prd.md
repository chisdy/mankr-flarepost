## 1. 背景与问题

个人站长 / 独立创作者通常已有域名，但长期个人邮箱要么依赖付费套件（Google Workspace、Fastmail 等），要么落到体验割裂的临时邮箱或偏「发信 API 平台」的工具。

两个开源参考分别代表不同叙事：

- **vmail**：临时邮箱、免注册、收为主，可开放 API。
- **emailflare**：事务性发信平台、管理台、模板、scoped API Key。

两者都不足以直接当作「个人域名邮件客户端」。本产品要填补的是：**在绝对零成本前提下，为自己的域名提供可日常使用的轻量 Web 收发信客户端，并可被他人按文档零成本复现部署。**

---

## 2. 产品定位

**一句话：**  
面向个人站长的、可自托管的轻量域名邮件客户端：在绝对零成本前提下，用现代 Web UI 完成日常收发信。

**目标用户：**  
拥有（或即将拥有）独立域名、需要自用邮箱、不愿为邮箱付费、能接受自行部署的个人开发者或独立创作者。

**产品形态：**

- 单用户、单实例自托管
- V1 单域名；同一登录身份下管理 2–5 个别名地址
- Web 邮件客户端（收件箱 / 写信 / 回复 / 基础文件夹）
- 支持一键部署到 Cloudflare；部署文档属于产品验收的一部分

**选定方案：** 纯个人域名邮件客户端（非临时邮、非发信 SaaS）。

### 2.1 最高指导原则

1. **Total Free（绝对零成本）**  
   所有选型与能力必须可在无需绑定信用卡的免费层内永久运行。任何会逼用户付费才能维持核心闭环的能力，默认砍掉或降级到后续版本。

2. **个人客户端，不是平台**  
   不做临时邮箱产品、不做多租户公开 SaaS、不做事务/营销发信平台。

3. **轻量可用优先**  
   V1 只保证：收、读、写、回、删 + 基础文件夹闭环。

4. **可部署即产品的一部分**  
   提供一键部署到 Cloudflare 的能力；「第二人可借一键部署（或文档兜底）在免费层完成同等闭环」是成功标准，不只是代码能跑。

### 2.2 与参考项目的关系

| 参考 | 借鉴 | 不借鉴 |
|------|------|--------|
| vmail | 边缘收信自托管心智、轻量 Web 用邮体验 | 临时邮箱主叙事、免注册即用、Open API |
| emailflare | 发信能力边界意识、配置/管理思路 | 模板系统、scoped API Key、多服务管理台 |

## 3. 目标与非目标

### 3.1 目标（Goals）

- 为个人域名提供可用的 Web 收发信客户端
- 单用户账号密码鉴权，管理少量别名
- 在免费层约束内完成可验证的日常通信闭环
- 提供一键部署到 Cloudflare，并辅以完整自托管文档，使他人可复现部署

### 3.2 非目标（Non-Goals）

本产品 **不是**：

- 临时邮箱 / 一次性邮箱服务
- 事务邮件 / 营销发信平台
- 多租户公开 SaaS（他人在你的实例上注册使用）
- 完整企业邮（共享邮箱、委派、合规审计套件）
- IMAP/SMTP 桌面客户端生态的替代品（V1 仅 Web）

V1 **明确不做**：附件、搜索、标签、过滤器、自定义文件夹、多域名实装、Open API、多用户、日历/联系人 CRM。

## 4. 用户与场景

**主角：** 唯一管理员用户（部署者本人）。无公开注册入口；账号在部署/初始化时创建。

**登录身份与别名：** V1 只有一个登录主体（一个用户名/主账号 + 一个密码）。2–5 个别名是该主体下的收发地址，不是多个独立登录账号。用户名建议使用主别名邮箱地址，但不要求每个别名各有一套密码。

### 4.1 核心用户故事（V1 Must）

1. **部署与开通** — 通过一键部署到 Cloudflare（失败或进阶场景可用文档兜底）完成部署，并绑定自己的域名，全程无需付费。
2. **登录** — 使用邮箱账号 + 密码登录，仅本人可访问邮件。
3. **管理别名** — 在同一域名下创建/停用 2–5 个邮箱别名；仍为同一登录身份。
4. **收信** — 发到已启用别名的邮件进入收件箱。
5. **读信** — 查看发件人、主题、时间、正文（纯文本 / 安全展示的 HTML）。
6. **写信 / 回复** — 选择别名作为发件人写新信或回复；成功则进入已发送。
7. **整理** — 删除到垃圾箱、恢复、清空；在收件箱 / 已发送 / 垃圾箱间切换。
8. **他人复用** — 另一人通过一键部署（或同一文档兜底）完成零成本部署并获得同等闭环。

### 4.2 V1 不做的场景

- 多人各自独立账号协作
- 临时一次性邮箱、公开创建邮箱
- 程序化 Open API
- 搜索、星标、标签、过滤器、附件、联系人、日历
- 多域名同时收发（仅路线图占位）

### 4.3 成功画面

部署者通过一键部署到 Cloudflare，并用自己的域名完成设置后，能用主别名接收一封外部邮件、阅读、回复并看到已发送记录；第二人也能借同一套一键部署路径（文档作兜底）在免费层复现同一闭环。

## 5. 功能范围与优先级

技术实现方式不在本文展开。

### 5.1 P0 — V1 必须交付

| 模块 | 能力 | 说明 |
|------|------|------|
| 访问与鉴权 | 账号 + 密码登录 / 登出；可修改密码 | 单用户单凭证；改密码为 P0 能力，不必依赖完整设置页 |
| 别名管理 | 创建、启用/停用、列表 | 单域名下 2–5 个；可设默认发件别名 |
| 收件 | 接收并入库到对应别名 | 仅已启用别名进入产品收件箱 |
| 收件箱 | 列表、打开详情、标记已读（列表态即可） | 按时间倒序；发件人 / 主题 / 时间摘要 |
| 读信 | 主题、收发件人、时间、正文 | HTML 需安全渲染；V1 无附件下载 |
| 写信 | 新邮件：选发件别名、收件人、主题、正文 | 纯文本优先；富文本若做必须极简 |
| 回复 | 一键回复 | 发件别名默认用原收件别名；引用上下文为佳但非硬性 |
| 已发送 | 成功发出的邮件可查 | 失败需有可见错误提示 |
| 删除与垃圾箱 | 删到垃圾箱、恢复、清空 | 基础三态文件夹 |
| 文件夹导航 | 收件箱 / 已发送 / 垃圾箱 | 不做自定义文件夹 |
| 部署体验 | **一键部署到 Cloudflare** + 自托管说明 + 域名/配置检查清单 | 一键部署为 P0 主路径；文档为失败/进阶兜底；「别人也能零成本部署」属验收项 |
| 免费约束可见 | 能力边界在产品或文档中写明 | 别名上限、无附件、配额相关预期等 |

### 5.2 P1 — 可放入 V1 尾巴，不阻塞主验收

| 模块 | 能力 |
|------|------|
| 草稿 | 手动保存草稿（非自动） |
| 转发 | 转发原信到外部地址 |
| 基础设置页 | 集中管理默认发件别名、显示名；改密码入口可收敛至此（改密码能力本身属 P0） |
| 空态与引导 | 首次登录引导「如何绑定域名 / 如何测收信」 |
| 移动端可读 | 响应式可用即可，不做独立 App |

### 5.3 P2 — 后续方向（仅占位）

- 多域名
- 附件（须带严格大小上限，且不得破坏 Total Free）
- 搜索、星标、标签、过滤器
- 多用户
- Open API / Webhook
- 临时别名
- Passkey / 魔法链接
- 联系人、签名模板库、规则引擎

## 6. 关键产品规则

1. **别名上限硬顶 5**：超过则拒绝创建，并提示免费层策略。
2. **无附件（V1）**：  
   - 发信 UI 不提供附件入口；  
   - 收信若含附件，可提示「不支持附件」并仍展示正文。
3. **单用户**：不提供注册入口；账号在部署/初始化时创建。
4. **单域名（V1）**：多域名仅作为后续方向，不进入本版本范围。
5. **发信失败可理解**：用户须能区分至少「未配置发信 / 限额 / 地址无效」等类别（具体枚举由实现/架构阶段定义）。
6. **安全底线（需求表述）**：未登录不可访问邮件内容；登出后会话失效。
7. **未启用别名**：发往未启用地址的邮件不进入产品收件箱（实现策略在架构文档细化）。
8. **一键部署优先**：对外推荐路径是一键部署到 Cloudflare；文档必须覆盖一键部署成功后的域名绑定与验证步骤，以及一键部署不可用时的手工兜底。

---

## 7. 约束

1. **绝对零成本**：无需绑信用卡即可永久运行；P0 不得依赖付费才能维持的能力。
2. **自托管单实例**：一份部署服务一个站长。
3. **轻量交互闭环优先于功能宽度**。
4. **技术选型与架构另文编写**：本文不绑定具体 Cloudflare 产品组合或第三方免费发信渠道细节；该部分后续单独产出。

## 8. 验收标准（Definition of Done）

### 8.1 功能闭环

- [ ] 初始化后可用账号密码登录 / 登出
- [ ] 可创建并管理 ≤5 个别名，可设默认发件别名
- [ ] 外部发到已启用别名的邮件出现在收件箱并可阅读
- [ ] 可从某别名新写信并进入已发送（或明确失败原因）
- [ ] 可回复一封已收邮件
- [ ] 可删除到垃圾箱、恢复、清空
- [ ] 未登录无法访问邮件数据

### 8.2 可部署复用

- [ ] 提供一键部署到 Cloudflare 的主路径（具体载体在架构文档定义，如官方 Deploy 按钮 / 自动化流水线等）
- [ ] 一键部署后，用户仅需完成域名邮件相关配置与初始化账号，即可进入收发闭环
- [ ] 存在完整自托管文档作为兜底（前置条件、配置项、域名邮件检查清单、验证步骤、一键部署失败时的排查）
- [ ] 第二人可借一键部署（文档兜底）+ 免费层资源完成同等闭环（由部署者或协作者实测一次）

### 8.3 免费原则落地

- [ ] 文档与产品内写明 V1 能力边界（别名上限、无附件、单用户单域名等）
- [ ] P0 功能列表中无「必须付费才能用」的依赖项（在架构文档阶段逐项核对）

## 9. 风险与预期管理（产品侧）

| 风险 | 产品预期 |
|------|----------|
| 免费层发信到达率不稳定 | V1 定位「个人轻量可用」，不承诺企业级送达率；失败须可解释 |
| 无附件限制部分日常场景 | 接受；文档明确；附件进 P2 |
| 垃圾邮件 / 滥用 | V1 仅收已启用别名，降低噪音 |
| 用户期望完整 Gmail 体验 | 用非目标与 P0 边界管理预期 |
