# Mankr Flarepost 功能拓展分析

分析日期：2026-11-04。对象：当前工作区代码、迁移、README、产品与设计文档，以及本地收件箱和设置页面。

本文是产品与架构分析，不是已完成的功能验收或安全审计。没有修改业务代码、调用真实发信或更改邮箱设置；未验证生产部署、真实投递质量、移动设备推送及大数据量性能。工作区已有未提交的界面改动，分析以当前文件为准。

## 1. 核心判断

项目已经跨过“能不能收发邮件”的阶段，下一步应优先解决“能不能长期作为主力域名邮箱使用”。最有价值的方向是：

1. 提高日常处理效率：批量操作、归档、未读管理、高级搜索。
2. 补齐通信语义：Cc/Bcc、Reply-To、标准回复头、会话视图、联系人与签名。
3. 让邮件与数据状态可信：防重复发送、投递状态、收信去重、备份恢复、域名诊断。
4. 发展符合个人站长场景的特色：地址用途隔离、稍后处理、轻量通知、邮件转个人任务。
5. 把附件、AI、多域名作为可选扩展；多用户、IMAP/SMTP 服务端、营销平台作为独立产品决策。

推荐定位：**个人站长的域名通信工作台**。保留一个实例、一个使用者、简单部署的优势，同时让它更适合处理项目往来、域名续费、账单、站点通知和合作邮件。

这份优先级是根据产品定位与当前功能断点作出的判断，尚无访谈、活跃用户数据或行为埋点支持。后续应以真实使用反馈校正。

| 运维 | 用量页、平台配额读取、垃圾箱/垃圾邮件保留天数、定时清理 | 尚无产品化备份恢复、端到端健康诊断与异常中心 |
| 使用体验 | 中英文、主题设置、响应式布局、首次引导 | 浏览器检查只覆盖桌面页面；移动端能力仍需专项验收 |

### 2.1 文档差异必须先厘清

- 早期 PRD 把搜索、标签、过滤器、Open API 等列为后续，而当前已实现。不能继续把这些当作新增功能排期。
- 早期架构中的默认 Cloudflare 发信、Mailchannels 等已与当前三渠道实现不同。
- `2026-07-26-attachments-design.md` 描述 R2 附件方案，但迁移先创建、后删除了附件表，当前 Worker 没有附件存储绑定。该设计可作历史参考，不能视为已有能力。
- `MAX_ALIASES = 5`、`MAX_TAGS = 50` 是应用设置的上限，不是由这两处代码证明的 Cloudflare 平台配额。调整需要容量与产品评估，而不是天然需要升级平台套餐。
- “免费层内运行”与“无需支付方式开通”是两个条件。当前文档强调二者都要满足，扩展规划应分别检查。

建议先维护一份与当前实现一致的能力矩阵，将历史设计标注为“已实现 / 已撤回 / 待重新评估”，降低后续误判成本。

## 3. 当前架构带来的机会与限制

当前结构是 React SPA + Hono API + Email handler + D1 + 可插拔发信适配器，静态资源与 API 同 Worker 部署。它很适合继续承载个人邮件应用，近期扩展无需拆微服务或更换框架。

| 扩展类别 | 现有基础 | 实施含义 |
| --- | --- | --- |
| 列表、搜索、整理 | messages 服务、标签关系表、游标分页 | 适合增量扩展；注意查询索引与跨页批量语义 |
| 联系人与身份 | aliases、发信记录、设置页 | 可增加小型表；不需要引入 CRM |
| 自动化 | 入站规则引擎、scheduled handler | 可复用触发入口；外发动作需另有任务和重试机制 |
| 投递可靠性 | SendAdapter、provider message id、用量事件 | 可统一状态；必须处理各平台能力不一致 |
| 附件 | 历史方案可参考，但无当前存储链路 | 属于重新引入的纵向能力，覆盖收、存、读、发、删全链路 |
| 多域名 | messages 已关联 alias | 仍需域名实体、配置验证和适配器身份映射，不能只放开输入框 |
| 多用户 | 业务数据按单使用者设计，没有普遍的 owner 隔离 | 是权限与数据模型重构，不能只加注册页 |

### 3.1 建议随功能演进补齐的数据基础

1. **邮件通信元数据**：RFC Message-ID、In-Reply-To、References、原始 Reply-To、To/Cc、发件人显示名、原始邮件日期与接收时间。Bcc 应作为发件人侧私有数据处理，不能泄露进外发可见头。
2. **状态分离**：收信/发信方向、用户整理状态、发送任务状态、上游投递状态分别表达。归档不是删除，API 接收成功不是送达。
3. **可靠发送**：发送任务与 attempts、幂等键、provider 与 provider message id、任务认领、失败分类、未知状态与人工重试。
4. **增量同步**：邮件更新时间、草稿版本、邮箱变更版本，支撑轻量刷新、缓存失效和多标签页同步。
5. **扩展设置拆表**：contacts、alias profiles/signatures、saved searches、reminders 等按职责增加；避免将整个产品状态堆进单行 mailbox_settings。

这些是方向性建议，不应为了未来一次性全部建表。每个字段随对应功能迁移和验收一起落地。

## 4. 全面功能候选与优先级

优先级定义：**P0** 为下一阶段应优先解决的可用性或可靠性问题；**P1** 为高价值增强；**P2** 为验证需求后开发的可选能力；**P3** 为暂缓或改变产品定位的方向。这里的 P0/P1 是本报告重新排序，不等同于历史 PRD 的版本命名。

工作量为熟悉本项目的一名全栈开发者的粗估，含基础迁移、界面、中英文与必要验证：S=1–3 人日，M=4–8 人日，L=9–15 人日，XL=超过 15 人日。复杂协议、三平台联调、性能和迁移问题可使估算明显增加；各行不可简单相加为交付承诺。

## 5. 最值得先深入的九个方向

### 5.1 批量整理 + 归档：最直接的日常收益

当前星标是单封开关，整理主要在详情页进行。处理几十封构建通知或账单时，需要反复打开邮件。

第一版应包括本页多选、Shift 连选或简单全选、批量已读/未读、归档、标签和移入垃圾箱。明确“选中本页 50 封”和“选中全部搜索结果”是两种操作；先交付前者。不要用前端同时发出上百个单封请求替代批量接口。

归档需要先决定是增加 `archive` 文件夹，还是独立表达“是否在收件箱”。当前 folder 有 CHECK 约束、前端联合类型与恢复逻辑，不能只增加导航项。若第一版采用 archive 文件夹，还需记录从归档移到垃圾箱之前的位置，避免恢复后一律回到 inbox/sent。

验收示例：选中 20 封通知一次归档，收件箱与侧栏计数更新，全部邮件和搜索仍能找到；撤销或恢复不会改变原始收发方向。全部邮件的包含范围需明确，建议默认不含草稿、垃圾箱和垃圾邮件。

### 5.2 Cc/Bcc、回复全部与会话：作为一个通信基础包设计

当前 MIME 解析与邮件结构没有保留完整的原始收件人和回复链字段。入站写入的 toAddrs 来自实际投递地址 `message.to`，这不足以支撑回复全部。回复 UI 已有，但 `replyToMessageId` 没有转化为完整的标准线程元数据；恢复草稿也需要保留其回复上下文。

先补存储和三渠道输入契约，再做界面。正确区分：原始来信的 Reply-To 决定回复目标；外发邮件的 Reply-To 决定对方后续应回复谁；In-Reply-To/References 用于会话关系。三个概念不能互相替代。

验收包括多人往来、跨别名、自身地址去重、回复草稿重新打开、Bcc 不泄露、外部邮箱正确串联。旧邮件缺失的头信息无法凭空恢复，应允许保持单封，不宜只按相同主题强行合并。

### 5.3 联系人 + 签名 + 个人模板：成本较低的使用频率提升

联系人第一阶段从最近实际发送记录产生建议即可，支持显式保存、删除和更名。不要默认把所有垃圾邮件发件人收入常用联系人。

签名按别名配置，而不是只有一个全局签名。新信与回复可分别开关，编辑后切换发件身份不能无限追加重复签名。当前显示名主要用于应用菜单，不能直接视为已经支持外发身份显示名。

模板限定为个人片段，例如合作回复、问题排查信息和项目交付说明；保留人工预览与发送。无需为此引入营销名单、活动管理和批量投放。

### 5.4 搜索增强：先解决条件表达，再评估全文索引

先增加可组合的发件人、收件人、日期区间、别名、标签、未读、星标筛选；支持保存“本月账单”“待回复合作”等视图。高级表单和 `from:` / `after:` 等语法可共享一个查询模型。

星标、标签、文件夹等筛选应能组合，避免继续扩展互斥分支。全文搜索不是高级筛选的前置条件。D1 支持 FTS5，但中文与混合语言搜索的分词、子串匹配、高亮和召回需要专门验证，不能认为换成 MATCH 就一定比当前 LIKE 更好。[D1 SQL 支持](https://developers.cloudflare.com/d1/sql-api/sql-statements/)

先测不同邮件数量下的查询时延、读取行数与用户是否找得到目标，再决定索引方案。

### 5.5 可靠发送与投递状态：先避免重复，再增加自动重试

当前流程先调用上游，再记用量、写入已发送、删除草稿。由此可以推断：上游已经接受但后续数据库写入或客户端响应失败时，用户可能看到失败，却已经发出；直接重试可能重复发送。这是静态流程分析，尚未通过故障注入复现。

建议引入发送任务与幂等键，状态至少区分“待发送、处理中、平台已接受、结果未知、失败”。记录 provider 和每次尝试，超时保持未知并提供核对入口。不能对未知结果一律自动换平台重发，因为不同平台无法共享去重状态。

Resend 支持幂等键，可复用同一请求的结果；其保证窗口有期限，不能代替应用自己的任务记录。其他适配器逐个核对能力，缺失时展示明确的能力差异。[Resend 幂等](https://resend.com/docs/dashboard/emails/idempotency-keys)

随后接入投递事件，增加“对方服务器已接收、临时延迟、退信”等状态。“服务器已接收”不代表进入收件箱，也不代表用户已读。Webhook 需要验签、事件去重及乱序处理；每位收件人的结果可能不同。[Resend 事件定义](https://resend.com/docs/webhooks/event-types)

### 5.6 数据可携带与恢复：让人愿意长期存邮件

第一版先提供版本化 JSON 导出，覆盖邮件、别名、标签、规则、设置及其关联关系，并提供恢复预检查和计数报告。明确密钥和管理员凭证是否导出，默认避免无保护地打包秘密。

后续支持 EML/MBOX。由于当前没有保存原始 MIME，且来信附件已经丢弃，不能承诺从历史数据导出完全原样的 EML，也不能恢复旧附件。重建邮件文件与保留原始邮件是两种能力，文案须说明。

D1 Time Travel 可作为运维恢复手段，但不是用户跨实例迁移格式。恢复流程还要考虑 COOKIES_SECRET：数据库中的发信密钥依赖它加密，换实例后只恢复 D1 不一定能解密，应要求保留原 secret 或重新配置渠道密钥。

验收以新实例恢复后邮件数、标签关系、别名状态及规则一致为准，不能以“下载了一个 JSON”作为完成。

### 5.7 域名诊断与健康页：把一键部署变成可用部署

将现有文字引导升级为状态检查：域名是否设置、别名是否启用、MX 是否符合预期、SPF 是否重复或缺失、DMARC 是否存在、已知 selector 的 DKIM 是否可查询、活动发信渠道是否有凭证。

DNS 记录存在不等于配置有效，DKIM selector 也无法普遍自动猜出。权限不足或无法确定时显示“未验证”，避免显示绿色成功。收信链路最终需要一封带相关标识的测试来信；发信链路需要用户触发测试并观察结果，不能只看密钥是否填写。

健康页应显示最近一次成功入站、成功提交、失败原因、清理任务结果与数据时间。缓存 DNS 和平台查询，避免每次打开页面都消耗外部 API。

### 5.8 地址用途管理：适合个人域名的特色

将别名从地址列表扩展为身份：用途、说明、显示名、签名、默认回复身份和相关统计。适合区分个人、合作、账单、站点服务。

进一步评估 `me+shop@domain` 的接收归一化和用途标签。Cloudflare 官方说明路由支持加号寻址，Worker 中 `message.to` 保留 detail；当前应用按完整地址匹配，所以平台能路由不代表应用已经接收。[Cloudflare 路由地址规则](https://developers.cloudflare.com/email-service/configuration/email-routing-addresses/)

先通过真实收信验证大小写、plus detail 与别名停用语义。仅做接收用途地址比支持任意地址外发更容易。无限随机地址、公开临时邮箱与任意反向匿名回复都应单独决策，不能因已有 catch-all 就默认开启。

### 5.9 稍后处理与个人任务：比泛化协作平台更贴近场景

支持“明天处理”“下周提醒”和“等待对方回复”。可以复用现有定时入口，但待回复状态需要会话模型，否则仅靠主题关键词容易误判。

第一版只做站内提醒和列表，不必立刻加入第三方任务同步。后续允许用户将一封邮件转成自己的任务，保留回链、到期时间和完成状态。

定时发送和撤销发送可随后接入同一个任务基础。“撤销发送”只能在应用延迟提交窗口内取消，无法撤回已被上游接受的邮件；时间精度和时区必须明确。

## 6. 三个需要单独决策的方向

### 6.1 附件：价值高，但不能当作小补丁

当前收信会丢弃附件字节，仅保留提示。因此后续启用附件只能影响新邮件，不能找回历史附件。

可选路径：

| 路径 | 体验与成本 | 建议 |
| --- | --- | --- |
| 保持默认无附件 | 维持简单部署和原有开通约束；限制真实用邮场景 | 保留为基础安装模式 |
| 可选 R2 或自带对象存储 | 需要开通/凭证、存储限制和清理；可覆盖正常附件 | 推荐作为可选功能包 |
| 临时转发到已验证外部邮箱 | 依赖外部邮箱；须确认保留原信与附件的实际行为 | 作为过渡方案验证，不默认转发 |
| D1 存小文件或 Base64 | 占用正文数据库与读写预算；难覆盖常见附件 | 不建议作为通用附件架构 |

R2 有免费额度，但官方要求先开通订阅并完成 checkout，超额按用量计费；这不能自动等同于项目的“无需支付方式”承诺。具体开通要求需按账号核实。[R2 开通](https://developers.cloudflare.com/r2/get-started/)、[R2 计价](https://developers.cloudflare.com/r2/pricing/)

完整范围至少包括：入站大小与数量限制、元数据、私有鉴权下载、安全文件名、内联图片、草稿上传、三渠道发送能力、物理删除、孤儿清理、导出恢复。历史设计的“5 MiB/文件、5 文件、10 MiB/邮件”可作为讨论起点，不能直接视为三个发信渠道都支持的统一限制。

### 6.2 AI：适合可选助手，不适合作为默认核心依赖

优先范围为用户主动触发的摘要、翻译、改写和回复草稿。采用自带密钥或可选模型提供方，按请求展示成本/额度，并尽量只发送所需内容。邮件正文是不可信输入，不能允许其中的指令触发读取其他邮件、调用工具或自动发送。

不优先做全邮箱持续向量化、默认上传历史邮件、自动回复和自动外发。这些会增加持续成本、隐私和错误发送处理负担。先做小样本用户验证，衡量节省的时间、采纳率与成本，而不是以模型接入作为价值证明。

### 6.3 多域名与多用户：两种不同规模的改变

多域名仍可服务同一站长，具有自然延展性。需要 domain 实体、收信路由状态、发信验证、默认身份、筛选与配额归属。可在单用户架构上渐进实现。

多用户会要求所有业务查询有归属约束、权限隔离、共享与委派规则、邀请和恢复流程，并重新分配免费资源预算。应先确认是否要进入团队邮箱市场，再设计，不能以“users 表能多一行”推断已经接近完成。

## 7. 免费优先下的资源策略

截至本次官方文档核查，D1 Free 的单库上限为 500 MB，账号总量为 5 GB；每日读取 500 万行、写入 10 万行。当前应用是单 D1 部署，不能把账号 5 GB 总量当成当前单库可用量。[D1 限制](https://developers.cloudflare.com/d1/platform/limits/)、[D1 定价](https://developers.cloudflare.com/d1/platform/pricing/)

因此应优先：

- 列表只返回需要的字段。当前查询选择了 text_body/html_body，尽管列表返回结构没有正文；值得在性能改进时评估减少读取与反序列化开销。
- 先过滤再分页，避免每次刷新全量扫描正文。
- 新邮件刷新采用“前台启用、后台暂停、无变化退避、恢复前台检查”的策略。单标签页全天每 30 秒轮询约为 2,880 次请求，多标签页与全量计数查询会继续放大。
- 增量接口返回变化标识与必要摘要；只有变化时拉取当前列表，不将“实时”默认实现为持续全量刷新。
- 标签数量、别名数量可按产品策略配置，但应配合容量观察和清晰错误信息。
- 自动化、日志、全文索引各自有保留和清理策略；同时考虑索引带来的写入与空间成本。

Cloudflare 原生向任意收件人发信仍要求 Workers Paid，收信路由支持 Free。当前保留第三方可插拔发信符合免费优先路径；未来接入原生发信可作为付费能力适配，而不是默认替换。[Cloudflare Email Service](https://developers.cloudflare.com/email-service/)

“免费优先”应表达为在核定使用量与平台条款下可运行，不宜承诺无限容量或不受平台政策变化影响的永久零成本。

## 8. 可靠性与隐私：结合现有流程的改进点

以下是功能扩展需要的基础，不是漏洞已经被利用的结论：

| 当前可见事实 | 建议 |
| --- | --- |
| Web 发信限流使用每个 isolate 内的 Map | 如需可依赖的实例总配额，改为共享持久状态并设计原子预留/释放 |
| API Key 配额文档明确为非原子的软限制 | 对外保持明确语义；需要硬上限时使用条件更新或任务预留，核对失败释放 |
| 会话只含签名 userId 与过期时间，改密未更改会话版本 | 增加会话撤销或版本校验；改密可撤销旧设备；登出不应只被理解为服务端撤销所有令牌 |
| 登录路由未见应用级节流 | 增加有界、持久或平台层登录保护，并考虑错误提示与恢复 |
| HTML 用 DOMPurify 净化，没有专门的远程内容策略 | 增加远程图片/背景 URL 控制；净化脚本与防止追踪是不同目标 |
| 入站未保留 Message-ID，未见相关去重键 | 保存可信来源范围内的消息标识，结合投递地址设计去重；无标识邮件需明确回退策略 |
| 入站读取并解析整个原始消息，正文没有应用级大小策略 | 增加长度/体积边界和可理解的降级；不要无提示丢弃正文 |
| 规则在入库后执行，部分标签失败会跳过 | 增加规则执行摘要和失败可见性，回放时保证不会无限重复动作 |

第一阶段不必增加复杂审计平台；只需让用户能知道最近失败的操作、原因和可恢复方式。保留日志期限并避免默认记录完整邮件正文或秘密。

## 9. 推荐分阶段路线图

### 阶段 A：让日常使用更顺手

范围：批量整理、已读/未读、归档/全部邮件、刷新与新信提示、别名签名、近期联系人补全。

同时补最小登录保护和远程内容控制，统一现有文档能力矩阵。可以按独立小版本交付，不需要等待全部完成。

验收：一批通知无需逐封打开即可整理；常用收件人可补全；页面常驻能提示新信；归档可恢复且可搜索；图片加载选择对用户可见。

### 阶段 B：让通信正确、状态可信、数据可迁移

范围：Cc/Bcc、Reply-To 与标准回复头、发送幂等/未知状态、JSON 导出与恢复、域名健康诊断、会话撤销。

其中标准头和幂等任务先作为基础落地，再开发会话视图与投递反馈。收信 Message-ID 也在这一阶段开始保留，为未来逐步积累可串联数据。

验收：三渠道能力有明确矩阵；回复草稿重开仍保留上下文；重复请求不会盲目重复外发；新实例可恢复数据；配置错误有具体可定位信息。

### 阶段 C：提升长期效率

范围：高级搜索、保存视图、会话视图、规则试运行/回放、投递事件、待回复/稍后处理、PWA 与快捷键。

根据邮件规模决定是否加入 FTS5。根据真实用户的移动使用比例决定是否推进后台推送，而不是把推送当成 PWA 安装的自然结果。

验收：从数千封中按条件找信；历史规则先预览再应用；退信可见；用户能管理待处理邮件而不依赖反复星标。

### 阶段 D：验证特色与扩展模式

范围：用途化地址、多域名、可选附件、AI、只读收件 API/Webhook、定时发送。

每次只选一个主要方向做完整纵向闭环。先用访谈、需求投票或小范围使用验证决定顺序，避免同时增加存储、模型、协议和多用户复杂度。

### 若下一轮只能选五项

1. 批量整理 + 已读/未读。
2. 归档 + 全部邮件。
3. Cc/Bcc + 回复语义与标准头。
4. 防重复发送 + 结果未知可见。
5. JSON 导出 + 可验证的恢复。

若主要痛点是“部署者无法开通”，用域名诊断替换第 2 项；若主要痛点是“只能接收正文不能完成工作”，先决策可选附件模式并前移，不能机械坚持此排序。

## 10. 依赖顺序与实现落点

```text
通信头与地址模型 → 回复全部 → 会话视图 → 待回复/无回复提醒
发送任务 + 幂等 → 可控重试 → 定时发送/撤销窗口 → 可选渠道切换
批量 API + 整理状态 → 归档/标签批量操作 → 规则历史回放
组合查询模型 → 高级搜索/保存视图 → 按规模引入全文索引
版本化导出 → 恢复演练 → 导入迁移/自动备份
对象存储决策 → 附件收存读删 → 发信适配 → 附件导出恢复
```

| 代码区域 | 适合承载的变化 |
| --- | --- |
| `apps/worker/src/messages` | 批量操作、归档、组合查询、通信字段、导出 |
| `apps/worker/src/inbound` | 头解析、真实地址列表、体积边界、去重、附件入口 |
| `apps/worker/src/adapters/send` | Cc/Bcc、标准头、显示名、幂等与平台能力 |
| `apps/worker/src/send` | 发送任务、失败分类、API 幂等、状态查询 |
| `apps/worker/src/auth` 与 `http/middleware.ts` | 登录保护、会话撤销、身份恢复边界 |
| `apps/worker/src/filters` | 预览、回放、命中解释、可信/屏蔽规则 |
| `apps/worker/src/index.ts` | 现有定时入口的任务调度扩展 |
| `apps/web/src/features/mailbox` | 多选、筛选、刷新、归档与会话列表 |
| `apps/web/src/features/compose` | 联系人、签名、Cc/Bcc、草稿冲突、发送状态 |
| `apps/web/src/features/settings` 与 `usage` | 诊断、备份、可选能力、配额和失败状态 |

近期保持现有 Worker 单体与前端框架即可。是否引入查询缓存库，应取决于新信刷新、多视图同步、乐观更新的复杂度，不必先升级技术栈。可靠发送需要清晰状态机，但不必因此立即引入新的付费基础设施；先评估现有 D1 与定时触发的时间精度和吞吐是否够用。

## 11. 如何衡量做完后是否更有价值

单实例也可采用本地汇总、可选匿名反馈或手工使用记录，无需默认上传邮件内容。

| 目标 | 可观察指标 |
| --- | --- |
| 更易部署 | 从部署到首封真实收信/回信的时间；失败步骤分布 |
| 更易整理 | 整理 50 封邮件的操作次数与耗时；批量工具使用率 |
| 更易找信 | 典型查询成功率、响应时间、读取行数；中文搜索召回 |
| 更可信发送 | 未知状态数量、重复提交数量、可确认退信数量、恢复成功率 |
| 更安全地写信 | 草稿保存失败/冲突数；重新进入后的内容保留情况 |
| 更可迁移 | 新实例恢复演练通过率、数据计数与关联一致性 |
| 更符合免费目标 | D1 存储增长、每封新增读写量、每日刷新请求、渠道额度余量 |
| 更贴合目标用户 | 连续使用后的主要阻塞项：附件、找信、提醒、客户端接入或多域名 |

具体目标阈值需要先建立基线，本文不虚构活跃用户量、送达率或性能数据。
